# v0.5 release contract: deep explanation and comparison

Status: Approved on 2026-08-07.

Linear approval issue: [SIDPROJ-61](https://linear.app/yde/issue/SIDPROJ-61/v05-01-approve-the-v05-contract-and-known-truth-set)

## Goal

In real Chrome, a developer can select one v0.4 finding, record one bounded
follow-up interaction, see the first normalized Canvas2D command difference
and a bounded draw callsite, then compare that result with a second session.

The release passes only when controlled fixtures prove each explanation and
comparison result. External applications test whether the evidence is useful.
They do not define product truth.

## Baseline

v0.4 provides bounded investigation sessions, four candidate finding types,
Canvas2D method evidence, interaction associations, JSON export, and an honest
claim boundary. It does not export individual commands, capture draw stacks,
resolve source maps for draw calls, or compare two investigations.

The v0.4 API and `InvestigationSessionV1` stay compatible in v0.5.

## User stories

### US-1: Explain one finding

As a developer, I can select one saved finding and record the next matching
interaction with detailed evidence for that canvas only.

### US-2: See the command difference

As a developer, I can see the first normalized command difference between
consecutive active windows, or an honest reason why no difference is known.

### US-3: Find a draw callsite

As a developer, I can see a bounded stack for selected draw work and a mapped
development source location when a same-origin source map is available.

### US-4: Compare two investigations

As a developer, I can pair one baseline finding with one candidate finding and
see measured changes without an unsupported improvement claim.

### US-5: Export the evidence

As a developer, I can copy versioned explanation and comparison artifacts that
contain no raw application values or live browser objects.

## Core ritual

1. Record a baseline scenario with v0.4 recording.
2. Open one finding and select **Explain next interaction**.
3. Repeat the same interaction for at most 10 seconds.
4. Read the normalized command result and the selected callsite.
5. Keep the selected baseline finding and its session for comparison.
6. Make one application change and record the same scenario again.
7. Select one finding of the same type in the new session.
8. Compare the explicit pair and review measured changes and uncertainty.

The overlay keeps one baseline finding and its session in memory. It does not
persist a baseline across reloads. Programmatic users can retain the
deep-copied v0.4 session object or parse a previously copied session JSON
artifact.

## Scope boundary

v0.5 remains framework-neutral Canvas2D instrumentation. React owner data is
an optional adapter and is not required for command, callsite, or comparison
evidence.

v0.5 includes:

- One selected-canvas explanation capture.
- Normalized command entries and consecutive-window comparison.
- Bounded draw stacks and same-origin development source-map resolution.
- Explicit finding pairing across two `InvestigationSessionV1` artifacts.
- Exportable explanation and comparison artifacts.
- Controlled bad, fixed, variant, and nearest-negative fixtures.

v0.5 does not include:

- Global command or stack capture.
- Automatic canvas or finding matching across sessions.
- Pixel capture or visual equality.
- GPU, compositor, or browser rendering time.
- Production error reporting or remote artifact upload.
- Persistent investigation storage.
- Cross-origin source-map fetches.
- A causal React, interaction, or callsite claim.
- A claim that lower time in one pair proves an improvement.

## Public API

The v0.4 names and behavior remain release commitments:

- `startRecording()`
- `stopRecording()`
- `getLastSession()`
- `mark(label)`

v0.5 adds these names to the module and IIFE global:

- `startExplanation(selection)`
- `stopExplanation()`
- `getLastExplanation()`
- `compareSessions(baseline, candidate, pairing)`

Their public signatures are:

```ts
function startExplanation(
  selection: ExplanationSelection,
): ExplanationStartResult;
function stopExplanation(): ExplanationArtifactV1 | undefined;
function getLastExplanation(): ExplanationArtifactV1 | undefined;
function compareSessions(
  baseline: InvestigationSessionV1,
  candidate: InvestigationSessionV1,
  pairing: SessionFindingPairing,
): ComparisonArtifactV1;
```

The selection type is:

```ts
interface ExplanationSelection {
  sessionId: string;
  findingIndex: number;
}
```

`startExplanation()` accepts a finding only from the last completed session.
The finding's canvas must still be available. The method returns one of these
results:

```ts
type ExplanationStartResult =
  | { status: 'started' }
  | { status: 'already-active' }
  | {
      status: 'unavailable';
      reason:
        | 'no-session'
        | 'session-mismatch'
        | 'finding-not-found'
        | 'canvas-unavailable'
        | 'recording-active'
        | 'instrumentation-disabled';
    };
```

Starting an explanation starts a normal v0.4 recording and a selected detail
capture together. A second start is idempotent and returns `already-active`.
Starting an explanation during a normal recording returns `recording-active`
and preserves that recording.
`stopRecording()` and `stopExplanation()` both stop the shared recording. The
first stop creates both artifacts. A later stop returns no artifact.
Calling `stopExplanation()` during a normal recording returns no artifact and
does not stop that recording.

An explanation stops automatically after 10 seconds with
`stopReason: 'max-duration'`. A manual stop records `manual`. The normal v0.4
recording still uses its 30-second limit when no explanation is active.

`getLastExplanation()` returns a deep copy or no artifact. A new successful
explanation replaces the prior in-memory explanation only when it starts.

The comparison pairing type is:

```ts
interface SessionFindingPairing {
  baselineFindingIndex: number;
  candidateFindingIndex: number;
}
```

`compareSessions()` is a pure operation. It does not change recording state.
It accepts two `InvestigationSessionV1` values and an explicit finding pair.
It returns a deep-copied `ComparisonArtifactV1` with either `comparable` or
`incomparable` status. It does not throw for a missing finding, a finding-type
mismatch, or incomplete selected evidence.

## Explanation artifact

The explanation artifact has `schemaVersion: 1`. It contains:

- A unique explanation ID and capture times.
- The canvas-scan version and stop reason.
- The source session ID, finding index, finding type, and source canvas ID.
- The follow-up session ID and selected canvas ID.
- Normalized commands grouped by active window.
- Consecutive-window comparison results.
- The first known command difference.
- Bounded generated and mapped stack frames.
- Collection limits, drop counts, and unknown reasons.

The artifact does not contain:

- Raw strings, numbers, arrays, typed-array values, or object properties from
  Canvas2D arguments.
- Canvas or image pixels.
- Image URLs, application text, input values, or DOM snapshots.
- Raw argument objects or references to live objects.
- Source file contents, source-map `sourcesContent`, URL query strings, or URL
  fragments.
- The secret used to make capture-scoped value tokens.

Source file names, function names, and line and column values are allowed only
inside the selected callsite evidence. They are required to locate draw code.

## Selective command capture

The global passive and v0.4 recording paths do not allocate command entries or
capture stacks. Detailed capture runs only for the selected live canvas while
an explanation is active.

Each command entry contains:

- Its window-relative ordinal.
- `call` or `set` operation kind.
- The Canvas2D method or property name.
- Argument count and argument kinds.
- Capture-scoped opaque equality tokens for supported values.
- An `unknown` reason when safe normalization is not possible.

Value tokens meet these rules:

- Equal supported values inside one explanation receive the same token.
- Tokens differ across explanations, even for the same value.
- Tokens do not contain the raw value or a deterministic unsalted digest.
- Object tokens contain only a safe built-in kind and a capture-scoped ID.
- The artifact cannot use tokens to compare values across sessions.

Numbers use the existing 0.01 command-classification precision before the
capture-scoped token is made. Strings remain opaque. Arrays, typed arrays,
images, canvases, paths, gradients, and patterns remain opaque objects. The
capture does not invoke custom iterators, accessors, or application callbacks.

## Command comparison

The explanation compares each captured active window with the nearest prior
captured active window for the same selected canvas. It does not bridge a
dropped or unknown window.

The comparison scans command ordinals from the start. The first unequal entry
is the first difference. The reason is one of:

- `operation-kind`
- `operation-name`
- `argument-count`
- `argument-kind`
- `argument-token`
- `command-added`
- `command-removed`

The result for each window pair is:

- `same` when both complete normalized streams match.
- `changed` when a first difference is known.
- `unknown` when a cap, unsupported value, sampling gap, or missing reference
  prevents the comparison.

The overlay shows the first `changed` pair. If no pair changed, it says either
“No normalized command difference was observed” or “Command difference is
unknown.” It never converts `same` into “same pixels” or “wasted work.”

## Draw callsite evidence

The selected path captures at most one stack for the first raster operation in
the explanation. It can capture another stack for the current command at each
first changed ordinal, subject to the total stack limit.

Each stack frame can contain:

- A function name when the browser supplies one.
- A generated script path without query or fragment.
- A generated line and column.
- A mapped project-relative source path, line, and column when resolved.
- A mapping status and an honest unresolved reason.

Source-map lookup is limited to same-origin HTTP or HTTPS resources. It does
not follow a cross-origin map URL. It does not export map contents. If no safe
mapping exists, the generated frame remains available and the mapped source is
`unresolved`. The tool does not claim that a stack frame caused the finding.

## Collection limits

One explanation has these fixed limits:

- Maximum duration: 10,000 ms.
- Selected canvases: 1.
- Stored active windows: 120.
- Stored command entries: 5,000 total.
- Stored arguments per command: 20.
- Capture-scoped value tokens: 1,024.
- Stored stack samples: 8.
- Stored frames per stack: 20.
- Source-map lookups: 8.
- Maximum source-map response: 2 MiB per lookup.

After a limit is reached, normal v0.4 recording continues. Detailed entries
stop at that limit. The artifact records the dropped count and the first
affected coordinate. A command comparison is `unknown` only when a command
evidence limit affects that comparison. A callsite-only limit changes
`callsiteCoverage` and the related unresolved frame reason. It does not change
the command comparison status.

## Session comparison

Comparison uses explicit user pairing. It never matches by canvas ID, owner
name, array order, source path, or timing because those values can change
between sessions.

A pair is comparable only when:

- Both artifacts use `InvestigationSessionV1`.
- Both selected finding indexes exist.
- Both selected findings have the same finding type.
- The required finding evidence is present and not invalidated by a collection
  gap.

The comparison artifact has `schemaVersion: 1`. It records the session IDs,
selected finding snapshots, `pairingMethod: 'user-selected'`, measured values,
deltas, uncertainty, and the collection limits that affect the pair.

Every comparable pair includes these measures:

- Active window count.
- Raster operation count.
- Canvas2D API self-time.
- Maximum window self-time.
- Per-method operation counts and available self-time.
- Unknown command coverage.

It also includes finding-specific measures:

- Heavy work: episode operation count, episode self-time, and top methods.
- Repeated work: repeated windows, repeated operations, comparison gaps, and
  unknown windows.
- Resize churn: active resets, observed resets, affected episodes, and command
  statuses.
- Backing store: affected windows and maximum observed area ratio.

Structural counts use `increased`, `decreased`, or `unchanged`. Timing uses
“higher in this pair,” “lower in this pair,” or “equal in this pair.” Every
timing result sets `improvementEstablished: false`. A single pair never
produces “faster,” “regressed,” “fixed,” or “improved.”

An incomparable artifact contains exact reason codes and no delta claims. The
reasons include `finding-not-found`, `finding-type-mismatch`,
`unsupported-schema`, and `incomplete-evidence`.

The public comparison artifact shape is:

```ts
type ComparisonMeasureId =
  | 'active-window-count'
  | 'raster-operation-count'
  | 'canvas-api-self-time-ms'
  | 'maximum-window-self-time-ms'
  | 'unknown-command-window-count'
  | 'heavy-episode-operation-count'
  | 'heavy-episode-self-time-ms'
  | 'repeated-window-count'
  | 'repeated-raster-operation-count'
  | 'comparison-gap-count'
  | 'active-reset-count'
  | 'observed-reset-count'
  | 'affected-episode-count'
  | 'same-command-window-count'
  | 'changed-command-window-count'
  | 'affected-backing-window-count'
  | 'maximum-backing-area-ratio'
  | `method:${string}:operation-count`
  | `method:${string}:self-time-ms`;

interface ComparisonMeasure {
  id: ComparisonMeasureId;
  unit: 'count' | 'ms' | 'ratio';
  baseline: number | null;
  candidate: number | null;
  delta: number | null;
  direction: 'increased' | 'decreased' | 'unchanged' | 'unknown';
  interpretation: 'structural' | 'observed-timing-pair';
}

interface ComparisonFindingRef {
  sessionId: string;
  findingIndex: number;
  findingType: InvestigationFinding['type'] | null;
  canvasId: string | null;
}

interface ComparisonArtifactV1 {
  schemaVersion: 1;
  comparisonId: string;
  createdAt: string;
  canvasScanVersion: string;
  pairingMethod: 'user-selected';

```

## Known-truth fixtures

Controlled expected results come from fixture configuration outside the
canvas-scan runtime. Each behavior has three irrelevant variants and one
nearest negative.

### Command difference

The three positive variants change the same selected stream through different
wrapper depth, canvas order, and unrelated background activity. Each variant
has the same expected first difference.

The nearest negative repeats the complete normalized stream. It must report
`same` and no first difference.

The fixture also has one unsupported-value case. It must report `unknown`; it
must not guess a difference.

### Draw callsite

The three positive variants call the selected draw through direct, nested, and
bundled helper shapes. The expected project-relative file and line come from
fixture metadata, not from canvas-scan output.

The nearest negative omits a safe source map. It keeps the generated frame and
reports `unresolved`; it must not name the seeded source location.

### Session comparison

The three positive variants change session IDs, canvas creation order, and
unrelated canvas work. Explicit pairing must preserve the same structural
deltas.

The nearest negative pairs different finding types. It must return
`incomparable` with `finding-type-mismatch` and no deltas.

### Integrated user flow

One integrated fixture runs the complete ritual: baseline, selected
explanation, controlled application change, candidate recording, explicit
pairing, comparison, and export. Its bad and fixed causes stay structural and
outside canvas-scan output.

## Performance gates

The published v0.4 passive-path gates remain unchanged:

- Full capture: under 2 ms mean and under 3 ms p95 at 1,000 simple calls per
  frame.
- Count-only capture: under 0.75 ms mean and under 2 ms p95.
- When absolute browser timing is unreliable, paired candidate-minus-baseline
  delta is at most 0.25 ms mean and 0.5 ms p95.

With no active explanation, v0.5 must allocate zero command entries and capture
zero stacks. A structural counter proves this in the benchmark harness.

For the selected canvas at 1,000 simple calls per frame, detailed capture adds
less than 4 ms mean and less than 8 ms p95 over the v0.4 full-capture stream.
The benchmark reports both absolute and paired results. It fails on either
threshold when the browser run is stable.

## Release evidence

### Fixed-limit evidence

Each explanation artifact keeps `schemaVersion: 1`. It adds `limitResults` and
`callsiteCoverage`. `limitResults` always has these ordered names:
`duration-ms`, `selected-canvases`, `active-windows`, `command-entries`,
`arguments-per-command`, `value-tokens`, `stack-samples`, `frames-per-stack`,
`source-map-lookups`, and `source-map-response-bytes`.

Each result gives the fixed maximum, rejected count, reason, and first affected
coordinate. The matching count keys are `durationStops`,
`selectedCanvasRejections`, `activeWindows`, `commandEntries`,
`commandArguments`, `valueTokens`, `stackSamples`, `stackFrames`,
`sourceMapLookups`, and `sourceMapResponses`.

`firstGap` describes command evidence only. Callsite limits set
`callsiteCoverage` and frame unresolved reasons. A callsite limit does not make
a command comparison unknown. A finding-type mismatch uses public
`compareSessions()`, because the overlay hides different-type actions.

The mechanical release gate includes:

- `pnpm -r run typecheck`
- `pnpm --filter canvas-scan run test`
- `pnpm --filter canvas-scan run build`
- `pnpm --filter demo run build`
- `pnpm --filter dogfood run lab:v0.4`
- `pnpm --filter dogfood run lab:v0.5`
- `pnpm --filter dogfood run bench:chrome`
- `pnpm --filter dogfood run bench:v0.5:chrome`
- `node scripts/verify-pack.mjs`
- `git diff --check`

The v0.5 lab saves raw JSON and a machine-readable expected-result matrix. An
evidence checker rejects missing variants, missing nearest negatives, unknown
results presented as known, leaked raw values, and unsupported claim text.

The external acceptance run uses the remaining Excalidraw StaticCanvas
repeated-draw findings from the v0.4 post-release artifact. It must:

- Select one remaining finding.
- Capture one bounded explanation.
- Report the command result and callsite mapping status.
- Record a controlled second interaction when the application permits it.
- Compare an explicit same-type pair.
- Preserve diagnostics, drop counts, exact commands, commit hashes, package
  hashes, browser revision, and raw artifacts.

The external run can return useful evidence, `unknown`, or an unavailable
source map. It cannot prove a controlled product result and cannot block a
release only because Excalidraw does not expose a safe controlled change.

## Short human release test

Before publication, a person runs the integrated fixture in real Chrome and
confirms:

1. A finding has a clear **Explain next interaction** action.
2. The 10-second boundary and active state are clear.
3. The command result explains the first difference or the honest absence of
   one without exposing raw values.
4. The callsite is useful when mapped and honest when unresolved.
5. Baseline selection and explicit finding pairing are understandable.
6. The comparison uses measured pair language and makes no improvement claim.
7. Explanation and comparison JSON copy works.
8. A normal recording still works after the explanation ends.

Publication remains a HITL action. Signing, npm authentication, tag creation,
package publication, and final release notes need explicit user authority.

## Intervention conditions

AFK work stops for the user if implementation requires a change to:

- The public method names or argument shapes.
- The 10-second, command, stack, map, or performance limits.
- The selected-canvas-only boundary.
- The opaque-value privacy boundary.
- Explicit user pairing or the no-improvement claim rule.
- The controlled known-truth fixtures.
- The framework-neutral product boundary.

An environment failure in Chrome, Vite, source-map loading, npm, or signing is
reported as an environment failure. It does not become product evidence.
