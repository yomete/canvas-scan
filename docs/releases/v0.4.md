# v0.4 release contract: investigation sessions

Status: Approved on 2026-08-04.

## Goal

In real Chrome, a developer can record a bounded canvas scenario and receive
ranked, exportable evidence for continuous and burst-driven Canvas2D work.

The release passes only when the Canvas Performance Lab finds every seeded
v0.4 defect in bad mode and does not preserve that finding in fixed mode.

## Baseline

The v0.3.1 release already provides:

- One early import or script-tag installation.
- Main-thread Canvas2D method wrappers.
- Per-window raster operation counts.
- Total synchronous Canvas2D API self-time.
- `same`, `changed`, and `unknown` command status.
- Honest `unknownReason` values.
- React owner attribution with a confidence kind.
- A DOM-only overlay, inspect mode, source lookup, and JSON copy.
- A bounded 120-report history for at most 64 canvas lifetimes.
- Real-Chrome probes, package checks, and browser benchmarks.

The current product does not provide a recording session, per-method evidence,
draw episodes, interaction associations, lifecycle evidence, or a saved session
artifact. The global canvas record registry also keeps retired records in its
active iteration set.

## User stories

### US-1: Record one scenario

As a developer, I can start a recording, reproduce a slow interaction, stop
the recording, and keep canvas evidence from that bounded period.

### US-2: Find concentrated work

As a developer, I can find a canvas that performs costly Canvas2D work during
one load, zoom, pan, hover, search, filter, or resize interaction.

### US-3: Find repeated work

As a developer, I can find command-identical Canvas2D work during a continuous
animation or repeated interaction without treating it as proven waste.

### US-4: Find state and geometry churn

As a developer, I can find repeated resets and an oversized backing store with
the dimensions and activity that support the finding.

### US-5: Understand nearby browser activity

As a developer, I can see when a draw episode overlaps a recorded interaction
or long animation frame without receiving a causal claim.

### US-6: Share evidence

As a developer, I can export a versioned JSON artifact that another developer
can inspect without access to the live page.

## Public recording behavior

v0.4 adds one recording state machine:

`idle -> recording -> complete -> recording`

- The overlay exposes Record and Stop controls.
- The programmatic API exposes equivalent start, stop, and last-session access.
- Starting while already recording is idempotent and preserves the active
  session.
- Stopping while idle returns no session and changes no state.
- A recording stops automatically after 30 seconds.
- A manual stop records `manual` as the stop reason.
- An automatic stop records `max-duration` as the stop reason.
- Starting a new recording replaces the in-memory last session only after the
  new session starts successfully.
- Passive Scan behavior continues before and after a recording.

The public module and IIFE global expose these operations:

- `startRecording()`
- `stopRecording()`
- `getLastSession()`
- `mark(label)`

These names are release commitments and require public API tests.

## Session artifact

The exported session uses `schemaVersion: 1`. It contains deep-copied data and
does not expose internal mutable objects.

The artifact contains:

- A session ID, start time, end time, duration, and stop reason.
- The canvas-scan version and supported browser feature flags.
- Canvas identity, owner attribution, source location, and observed geometry.
- Active frame windows with a monotonic timestamp and stable window index.
- Canvas2D method counts and synchronous self-time by method.
- Command status, unknown reason, sampling state, and comparison gap.
- First-observed, active, detached, reactivated, and retired lifecycle events.
- Draw episodes and their canvas summaries.
- Recorded interactions, optional user marks, and long-frame entries.
- Explicit temporal associations between those entries and draw episodes.
- Ranked findings with evidence level, claim boundary, evidence, and next check.
- Collection limits, dropped-entry counts, and unsupported browser features.

The artifact must not contain:

- Canvas or image pixels.
- Raw Canvas2D argument objects.
- Input values or application text.
- Full DOM snapshots.
- References to live DOM, canvas, React, or browser objects.

## Bounded retention

- A session keeps at most 10,000 active canvas-window reports.
- A session keeps at most 128 observed canvas lifetimes.
- A session keeps at most 2,000 browser interaction and long-frame entries.
- The artifact records the number and type of entries dropped at each limit.
- The oldest complete entry leaves first when a limit is reached.
- A limit must not split one stored report or produce an invalid artifact.

The active record registry must not grow forever. DOM connection alone cannot
decide retirement because detached cache canvases remain valid draw sources.
A retired record must reactivate before its next wrapped Canvas2D call is
captured. Active and source canvases must keep their identity and dependency
tracking across retirement and reactivation.

## Draw episodes

A draw episode is a session-level group of nearby Canvas2D activity.

- An episode starts at the first frame boundary with Canvas2D activity after
  two consecutive inactive boundaries.
- Recording start establishes the initial idle state, so its first active
  boundary starts an episode.
- It includes each following boundary that contains Canvas2D activity.
- One inactive boundary inside an episode does not end it.
- Two consecutive inactive boundaries end it at the last active boundary.
- A continuous application produces one episode for the recorded interval.
- Multiple canvases can contribute to one episode.
- A recording stop closes the active episode without adding fake activity.

Each episode contains its start, end, active-window count, canvas summaries,
total method counts, Canvas2D API self-time, resets, geometry changes, and
temporal associations.

## Method evidence

The wrapper assigns each existing method duration to its Canvas2D method name.
It does not add another clock read per call. The session aggregates method
counts and self-time by canvas, window, and episode.

Property setters can contribute counts. v0.4 does not claim setter self-time
unless the wrapper measures that setter with the same native-behavior contract.

The method evidence must preserve count-only sampling behavior and the current
kill switch.

## Geometry evidence

Geometry collection runs only during a recording or for an actively selected
canvas. Passive Scan must not add a layout read for every canvas window.

The artifact records:

- Canvas backing width and height.
- Observed CSS width and height when available without retaining DOM objects.
- Device pixel ratio.
- The expected DPR-adjusted pixel area.
- The actual-to-expected backing-area ratio.

Zero-sized, disconnected, hidden, or unavailable CSS geometry produces an
unavailable reason. It does not produce a backing-store finding.

## Interaction and long-frame evidence

v0.4 feature-detects browser performance entries.

- `PerformanceEventTiming` supplies duration and `interactionId` when present.
- A document-level capture listener records timestamps for supported pointer,
  keyboard, wheel, input, and change events without wrapping app handlers.
- The public recording API accepts an optional short user mark.
- Long Animation Frame entries supply browser frame and script evidence when
  the browser supports them.
- Unsupported entry types appear in the artifact feature flags.

An entry associates with an episode only when their monotonic time ranges
overlap. A nearby event outside the episode range is not attached. Visible copy
uses “associated with” or “overlapped,” never “caused by.”

The artifact stores event type and a bounded target identity. It does not store
input values, text content, or a full DOM path.

## v0.4 findings

Each finding contains:

- A stable finding type.
- The relevant canvas and episode identities.
- `measured`, `associated`, or `candidate` evidence level.
- The measured values that triggered the finding.
- The least-specific plain-language explanation that the evidence supports.
- A clear statement of what the evidence does not establish.
- A next check.

The evidence level, supported explanation, and non-established statement form
the claim boundary.

v0.4 stops at the least-specific useful explanation. When commands, callsite
stacks, or source maps can narrow the explanation, the next check points to
that later work. v0.5 collects that evidence only for a selected finding.

### Canvas work summary

Every non-empty session ranks canvases by total Canvas2D API self-time, then by
maximum window self-time, then by raster operation count. This summary is
measured evidence and is not a warning.

A canvas receives a `heavy-canvas-work` candidate when one episode contains at
least 8 ms of Canvas2D API self-time. The visible evidence includes the top
methods, their counts and self-time, the maximum window, and any long-frame
overlap.

### Repeated draw work

A canvas receives a `repeated-draw-work` candidate when a recorded window has
`signatureStatus: same` and meets the configured minimum raster operation
count. The evidence includes repeated windows, repeated operations, observed
self-time, comparison gaps, and unknown coverage.

The finding must not describe the work as wasted or avoidable.

### Resize churn

A canvas receives a `resize-churn` candidate when reset events overlap active
raster work in at least two active raster-work windows. The evidence includes
the reset count, affected episodes, dimensions, and resulting unknown reasons.

Width and height setup in one active window does not produce this finding.

### Backing-store mismatch

A canvas receives a `backing-store-mismatch` candidate when these conditions
hold in at least two active windows:

- CSS geometry and device pixel ratio are available.
- Actual backing pixel area is at least twice the expected DPR-adjusted area.
- The canvas performs raster work in the affected windows.

The evidence includes actual dimensions, expected dimensions, area ratio, and
affected raster work. The next check asks the developer to check the sizing
policy and required image quality.

## Finding order and visible behavior

The findings view first sorts by Canvas2D API self-time attributed to the
evidence. It next sorts by affected raster operations. Stable finding type and
canvas identity break remaining ties.

Each card shows:

- The canvas owner or canvas identity.
- The finding and evidence level.
- The affected interaction or episode when available.
- The measured evidence.
- Unknown coverage and collection limits.
- A next check.
- An action to locate or inspect the canvas when it is visible.

The existing red flash remains navigation into evidence. It is not the primary
investigation result.

## Canvas Performance Lab

The existing workbench becomes the internal Canvas Performance Lab. The public
demo remains small and polished.

### Known-truth cases

v0.4 includes bad and fixed cases for:

- Heavy burst-driven Canvas2D work.
- Repeated continuous draw work.
- Resize churn during active drawing.
- An oversized backing store.
- Canvas detachment, retirement, and later reactivation.
- An interaction that overlaps a long animation frame when supported.
- A non-React burst canvas that still receives useful measured evidence.

Each case declares structural expectations outside the product runtime. The
runtime receives no private scenario label or expected finding.

Each known-truth behavior runs at least three deterministic variants that
preserve the defect and one nearest negative case. Each variant changes at
least two factors that do not define the defect. Across the complete matrix,
the changed factors cover:

- React and non-React ownership.
- Continuous and interaction-driven drawing.
- Canvas2D method mixes.
- Canvas creation order and identity.
- Device pixel ratio and visible geometry.
- One idle boundary and two idle boundaries.
- Pointer, wheel, and keyboard triggers.
- Work immediately below and above each numeric threshold.

The expected evidence or finding type and supported claim remain stable across
defect-preserving variants. Measured values can change. The lab result records
the invariant, the changed factors, and the expected result for every variant.

### Integrated continuous app

Bad mode includes a static layer redrawn during animation, repeated resets, and
an oversized backing store. Fixed mode keeps the same visible scene and input
while removing those seeded causes.

### Integrated burst-driven app

The app remains idle until load, zoom, pan, hover, search, filter, or resize.
Bad mode performs a heavy whole-flamegraph redraw, resets during active work,
and replaces a canvas during a query. Fixed mode keeps the same data and
interactions while reducing the seeded causes.

The lab runner performs deterministic interactions and prints
`CANVAS_LAB_V04: PASS` only when all structural expectations pass. It emits a
versioned JSON result for release evidence.

## Release gates

All of these checks must pass from the repository root unless a command names a
different directory:

```bash
pnpm -r run typecheck
pnpm --filter canvas-scan run test
pnpm --filter canvas-scan run build
pnpm --filter demo run build
pnpm --filter dogfood run lab:v0.4
pnpm --filter dogfood run bench:chrome
node scripts/verify-pack.mjs
git diff --check
```

The lab command must use installed real Chrome, not jsdom. The core suite must
include deterministic tests for every finding rule and every session limit.

Hot-path changes keep the published v0.3.1 absolute budgets:

- Full capture: less than 2 ms added mean and less than 3 ms added p95.
- Count-only capture: less than 0.75 ms added mean and less than 2 ms added p95.

If a stable host cannot reproduce an absolute result, the release must record a
paired v0.3.1-versus-candidate A/B result. The candidate cannot exceed the
baseline median by more than 0.25 ms mean or 0.5 ms p95. A benchmark-policy
change needs user intervention and cannot hide inside a feature issue.

The release report contains every command result, lab artifact, benchmark
result, known limit, plan deviation, and independent judge verdict.

## User release test

The user tests one release candidate against this short script:

1. Install canvas-scan with the documented early-load path.
2. Record one continuous scenario.
3. Record one burst-driven interaction.
4. Check whether the top findings are understandable and useful.
5. Export the session and inspect its plain-language evidence.

## Out of scope

- Selective raw command recording and first-command differences.
- Draw callsite stack capture and callsite source maps.
- Product-facing comparison between two saved sessions.
- Worker and transferred `OffscreenCanvas` instrumentation.
- WebGL and WebGPU.
- Production telemetry, remote storage, or uploads.
- Automatic code changes or upstream pull requests.
- A general JavaScript CPU profiler.

Those deep-explanation and comparison features belong to v0.5. Worker,
framework, CI-budget, and graphics-API expansion remain later milestones.
